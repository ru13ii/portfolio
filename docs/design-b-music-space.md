## 1. 今回の方針

**ピアノ、五線、音符でつくられた一つの空間に、RuBiiの名前と作品、プロフィールが収まっている。**

今回のユーザーの要望は、B案の方向を引き継ぎながら、楽譜だけに限定せず音楽空間として再構成すること、音楽のモチーフをポートフォリオと一体化すること、スマートフォンではアニメーション演出をなくすこと。

ピアノの輪郭を画面の区切りに使い、五線を作品の並びに使い、音符を試聴の入口に使う。どのモチーフにも情報を整理する役割、または操作する役割を持たせる。余白は、それぞれの作品の間にある静けさとして扱う。

現在の生成り・青みのインク色・くすんだ紫、明朝体とセリフ体、人物アイコン、広い余白を継承する。空間は平面のレイアウトとわずかな重なりで表現する。通常の縦スクロールで巡れる構成とする。

この資料は[前回の楽譜・アニメーション案](design-b-piano-interactions.md)を更新する現行案。前回の「独立した楽譜の帯」「スマホでも小さな押下演出を返す」という提案は、本案で置き換える。

## 2. モチーフと機能を一体にする

| 音楽のモチーフ | ポートフォリオ内で担う役割 | 具体的な見せ方 |
| --- | --- | --- |
| グランドピアノの曲線 | 名前・紹介・代表曲を包む冒頭の構図 | 蓋を上から見たような緩やかな輪郭で、濃い面と生成りの面を分ける。RuBiiの名前はその面の中へ置く |
| 鍵盤の並び | 選択肢のグループ | Works / About / Contactを、鍵盤の端を思わせる細い区切りのあるリンク群にする。Works内のジャンル選択も同じ形を使う |
| 五線 | 作品を整理する共通の軸 | 作品画像・曲名・試聴位置を、同じ線の流れに沿って配置する。線は文字と画像の領域で途切れる |
| 音符 | 曲を聴くための操作 | 五線の終点に、音符を思わせる楕円の再生ボタンを置く。「▶ 聴く」を必ず併記する |
| 小節線 | 一作品・一件のお知らせの境界 | 年、担当、起用先のまとまりを細い縦線で区切る。記事の区切りにも同じ線幅を使う |
| 譜面台 | プロフィールを読む面 | 人物画像と紹介文を同じ薄い紙面に載せ、トップのピアノの面から続く構成にする |

鍵盤や譜面を読める知識は操作の前提にしない。ナビゲーションの名称、曲名、担当、起用先は常に文字で示す。実在の譜面として音高や拍を読ませる箇所は、必要になった段階で本人の正しい譜面を使う。

## 3. トップの構図 — ピアノから作品へ線がつながる

### 最初の画面

上部には小さな人物アイコンと名義。右側のWorks / About / Contactは、生成りの鍵盤が三つ並ぶような一続きのナビゲーションにする。黒鍵を模した追加の装飾は増やさない。

冒頭の左から下へ、グランドピアノを思わせる濃い青灰の大きな曲線を置く。その中に大きなRuBiiと短い紹介文を配置する。右の生成りの領域には、代表曲「雨を待つ」の画像と曲名、担当、試聴操作を置く。

ピアノの面の端から細い線が伸び、代表曲の試聴ボタンへつながる。その線の間隔と高さを、下に続く作品一覧の基準にもする。最初の画面だけで、作り手の名前と代表曲の両方に触れられる。

```text
［人物 RuBii］                         │ Works │ About │ Contact │
                                      └── 鍵盤のような区切り ──┘

 ╭──────── ピアノの輪郭 ─────╮
 │                          ╰──╮      ┌──────────────────────┐
 │       R u B i i              │      │ 「雨を待つ」の画像   │
 │  感情豊かな音楽を。          │      └──────────────────────┘
 │                             ╰─ ─ ─ 雨を待つ ──────［▶ 聴く］
 ╰──────────────────────────── ─ ─ ─ 作詞・作曲 / 知声 ─ ─ ─ ─
                                  │
              線と余白のリズムが、次の作品へ続く
                                  │
 Works       02   ［作品画像］  おもかげ               ［▶ 聴く］
                  ──────────  作詞・作曲 / 起用先 ─────────────
```

図は配置の説明。実際の画面では線を5本ずつまとめ、文字や画像を横切る部分を抜く。名義や日本語の見出しを輪郭で切り落とさず、曲線の内側にも十分な余白を確保する。

### 空間としての奥行き

奥行きは「生成りの地」「濃いピアノの面」「作品と文字」の三層に限定する。作品画像は真っすぐ配置し、ごく薄い影で紙のような浮きを表す。本文を斜めに傾けず、視点を回転させる操作も要求しない。

ピアノの輪郭は抽象化し、初稿では輪郭と面だけで成立させる。新しい写真、3Dモデル、楽器イラストを必須素材にしない。

## 4. スクロールするとどう展開するか

| 区画 | 表示する情報 | 音楽空間とのつながり |
| --- | --- | --- |
| 冒頭 | RuBii、短い紹介、代表曲、試聴 | ピアノの面から、代表曲が載った五線へ視線が流れる |
| Worksへの入口 | 登録済み作品から少数を紹介、全作品へのリンク | 五線と小節線を作品の配置・区切りに使う |
| Aboutへの入口 | 人物アイコン、プロフィール要約、詳細へのリンク | 五線の端を紙面の余白へ収め、譜面台に置いた紹介ページとして読ませる |
| News | 日付と活動情報 | 五線を一本の罫線へ整理し、短い小節のように情報を並べる |
| Contactへの入口 | 依頼の案内、問い合わせリンク | 線が終止線のように収まり、その隣に明確な相談ボタンを置く |

縦方向のつながりは、同じ左端・線幅・余白の間隔を繰り返すことで表す。全画面を横切る巨大な一本のSVGは使わず、内容の長さに応じて区画ごとの線を組む。長い曲名や作品追加にも対応できる作りにする。

## 5. Works・About・Contactも同じ空間の中へ

### Works — 曲が並んだ五線

上部のジャンル選択は、全件・ポップス・バラード・エレクトロを横に並べた鍵盤風のボタン群にする。ボタン幅は文字が収まる大きさとし、等幅の細長い鍵盤へ無理に押し込めない。選択状態は濃い下線と枠で示す。

作品は「画像／曲名と説明／試聴」の横長のまとまり。年・担当・起用先はその下へ置く。五線は画像の左、情報の上下、試聴ボタンの手前にだけ見せ、文字の下は生成りの面を確保する。一作品の情報を一つの小節のように読める配置にする。

PCでは曲名にゆとりを持たせ、スマホでは画像 → 曲名 → 担当・起用先 → 試聴の順で縦へ組み直す。五線の端と音符型の試聴ボタンは残す。作品が増えても一曲ずつの見た目を特注せず、同じ構造へJSONの情報を流し込む。

### About — 作り手の譜面台

人物画像と文章を、一枚の大きな紙面の中へ収める。紙面の上端に小さな名義と細い線を置き、トップのピアノの色を端や台座に少量使う。人物画像は現在の400×400pxを生かし、大きく引き伸ばさない。

経歴が増えたら、年と出来事を縦に整理する。年表を実際の音符の位置へ置き換えるような、読み方を覚える必要のある表現は採らない。

### Contact — 音楽の続きを依頼する

見出しと相談の案内までにピアノの曲線や終止線の形を使い、入力欄は同じ紙面の上にそろえる。入力中に動く飾りは置かない。送信ボタンは通常の言葉で意味を伝え、FormspreeとXへの連絡方法を継続する。

## 6. PCの動きも、操作と空間をつなぐ

初稿では、動きは実際の選択・試聴の入口に集中させる。ポインターを置くと、対象となる作品と、その作品につながった線・音符が小さく反応する。

| 操作 | PCでの反応 | 動かさない部分 |
| --- | --- | --- |
| ナビゲーションにホバー | 鍵盤風リンクの下端だけが1px沈み、端の影が短く変わる | 文字とクリック範囲 |
| 作品の試聴ボタンにホバー | ボタン内の音符形が一度だけ2px浮いて戻る。その作品へ続く短い線の色も控えめに変わる | ボタンの外枠、曲名、担当、作品画像 |
| ジャンルを選択 | 下端が1px沈んで戻り、選択の下線が残る | 一覧の縦位置。カードはフェードさせず絞り込む |
| リンク・ボタンにキーボードでフォーカス | 明確なフォーカス枠を表示。条件が合うPCでは短い反応を添える | 操作の順序、文字の可読性 |

音符は1〜2個まで、動きは原則600ms以内で1回。押下を妨げない短い動きにする。同じ場所へ置き続けてもループさせず、連続操作で演出が積み重ならないようにする。ホバーで音は鳴らさない。試聴は「聴く」を押したときに開始し、アニメーションの完了を待たせない。

使われていない音符が勝手に漂う、画面全体がマウスを追う、スクロールでピアノが回転するといった演出は初稿に含めない。待機時は、整った静止画として成立させる。

## 7. スマートフォンはアニメーション演出なし

**スマホでは、サイト側の装飾・操作アニメーションをすべて無効にする。** 前案にあったタップ時の小さな押下演出も取りやめる。

- 音符の浮き・揺れ、鍵盤の沈み、ホバーの移動を行わない。
- フェードイン、スクロール連動、画面切り替えの演出を行わない。
- ボタンの色・枠・選択状態は即座に切り替える。変化の途中をアニメーション表示しない。
- サイトが指定するスムーズスクロールも使わず、通常のスクロールとページ移動にする。
- 音楽の形、五線の区切り、音符型の試聴ボタンは静止したまま表示する。

```text
［人物 RuBii］   Works  About  Contact

 ╭─ ピアノの曲線 ─────────────╮
 │ RuBii                     │
 │ 感情豊かな音楽を。        │
 ╰───────────────────────────╯
 ─── 代表曲 ──────────────────
 ［雨を待つ の作品画像］
 雨を待つ
 作詞・作曲 / 知声       ［▶ 聴く］
 ─────────────────────────────
 ［次の作品］
```

スマホでは横長の空間を縦へ組み替える。ピアノの面は紹介文を収める小さな区画にし、代表曲への到達を遅らせない。タブレットも初稿では静止を基本とする。

「演出なし」の対象は、サイト側で作る装飾とUIの動き。本人が操作して再生するYouTube動画・SoundCloud音源、ブラウザ自体の通常のスクロールは利用できる。外部プレーヤー内部の表示はそのサービス側の制御となる。

## 8. 一体感と見やすさを両立する基準

1. **すべてのモチーフに役割を割り当てる。** この線は何を区切るか、この音符はどの曲を聴く入口かを説明できる配置にする。
2. **ひと区画に主役は一つ。** 冒頭は名義と代表曲の関係、Worksは作品、Aboutは人物と文章を中心に組む。全モチーフを毎区画へ登場させない。
3. **五線は区切りと余白へ置く。** 本文やフォーム入力値には重ねない。画像の端で自然に途切れさせる。
4. **色は生成り・濃い青灰・くすんだ紫を基本にする。** 人物画像と作品画像の色は、そのまま各作品の見せ場にする。
5. **音符の形だけに意味を任せない。** 試聴は「▶ 聴く」、移動先はWorksなどの名称を併記する。
6. **押せる場所を明確にする。** 動かすのは操作要素の内部。五線やピアノの輪郭には、クリックできそうな反応を付けない。
7. **画面全体に使うピアノの大きな曲線は一つを基本にする。** 下の区画では、線の端や面の色を繰り返してつなぐ。
8. **PCも待機中は静止、スマホは常に演出なし。** 情報を探す視線と、動くものが競合しない状態を保つ。

採用判断では、音符を増やす前に「曲名と再生操作をすぐ見つけられるか」「モチーフと作品が同じ配置ルールで組まれているか」を確認する。

## 9. 実装時の方針

### 動きは静止を標準に、PCでだけ有効化

CSS・JavaScriptの標準状態を静止にする。アニメーションを有効にする候補条件は、画面幅1024px以上、ホバー可能、細かなポインター操作が可能、OSが動きの削減を要求していない、のすべてを満たす場合。1024pxは初稿のレイアウト基準として採用する値であり、端末名を完全に判別する仕組みではない。

スマホ相当の幅、タッチ中心の端末、動きを減らす設定では、CSSのアニメーションとトランジションを有効にせず、JavaScriptの演出も開始しない。PCのウィンドウを狭めた場合も静止となる。条件が変わったら進行中の動きを止め、静止状態へ戻す。

既存の共通CSSにあるhover時の拡大・移動、transition、smooth scrollも対象として見直す。新しい音符の動きだけ止めて既存の演出が残る状態を避ける。機能に必要な選択・フォーカス・送信状態は、即時の表示変更で伝える。

入力方法とOS設定を参照する仕組みは、[MDNのhover解説](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/hover)と[prefers-reduced-motion解説](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)を実装時の参照資料とする。

### 構成と更新

- Astro、Tailwind、JSON、既存URL、GitHub Pagesの構成を継続する。
- 文字・作品情報・操作は通常のHTMLで配置し、ピアノの輪郭や五線はCSSとSVGで構成する。画面全体を一枚の画像にしない。
- SVGの装飾は読み上げ対象から外し、操作の名前と順序はHTMLで明確にする。
- 共通の線幅・五線間隔・余白・曲線の扱いを定義し、トップと下層で同じルールを使う。
- 長い曲名・説明文・起用先でレイアウトが崩れないよう、情報の幅と改行を優先する。
- 編集ページでは現在と同じ内容を更新できるようにする。作品追加のたびに音符の座標を入力させない。
- 人物画像・作品画像・既存の文章で初稿を作れる。本人の実際の楽譜データは必須にしない。
- 曲に合わせた音符の発光、演奏機能、譜面の自動生成は追加機能として別途検討する。

## 10. 初稿で確かめたいこと

まずトップからWorksへのつながりを、PCとスマホの静的レイアウトで確認する。その後、PCのナビゲーションと試聴操作へ小さな動きを加える。

| 確認する場面 | 合格の目安 |
| --- | --- |
| トップの第一印象 | 名前・代表曲・ピアノの形が一つの構図として見える |
| 最初のスクロール | 冒頭の線や余白が作品一覧の配置へ続いている |
| Worksで曲を探す | 曲名・担当・起用先・試聴操作を装飾に隠されず読める |
| スマホの読み込み・タップ・絞り込み | サイト側の移動・揺れ・フェード・押下アニメーションが発生しない |
| スマホで試聴 | 一度のタップでプレーヤーを操作できる |
| PCでポインターを動かす | 対象の操作に関係する小さな反応だけが返る |
| 動きを減らす設定 | PCも静止し、操作の意味とフォーカス表示が残る |
| 長い曲名・多数の作品 | 文字が欠けず、同じ構造で作品を追加できる |

## 11. 合意と提案の区別

ユーザーの方向指定は、スマホのアニメーション演出をなくすこと、B案を基にピアノ・五線・音符の音楽空間へ広げること、その空間とポートフォリオを一体化すること。

本資料で追加した曲線の配置、鍵盤風ナビゲーション、音符型試聴ボタン、配色の面積、PCだけで動かす具体的な条件と数値は初稿用の設計提案。画面を見ながら調整する。

今回はデザイン資料の再構成。既存UIへの実装・コミット・プッシュは行わない。
